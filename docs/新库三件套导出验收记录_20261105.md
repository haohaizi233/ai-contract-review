## 已确认的问题

### P1：旧 OA 图片未本地化，图片覆盖状态又误报为“无”

位置：`tools/tender_case_export.py:1347` 的旧意见处理仅转换相对 URL 并写入缺口，不下载图片，也不尝试复用旧 MD 的本地化图片。`sec_flow()` 在第 1234 行附近仅统计新库意见图片，随后覆盖案件 image 状态。

样本中的申请 29809、37893、50650、1000001068、1000001619、1000003111 共 6 案，`_errors_sample.csv` 已报告旧 OA 图片缺口，但 `_index_sample.csv` 的意见图片列仍为“无”。样本图片汇总“1 张且全部本地”仅覆盖新库部分，不能代表全部案件意见图片。

建议：统一收集两种来源的图片引用，优先复用旧 MD 已有图片，再补抓有权限的旧 URL；统一计算总数、本地数及缺失数。若旧图片暂不能恢复，应标“有图片但未获取/部分缺失”，不能标“无”。

全量结束后进一步核对：旧 OA 图片缺口涉及 18425 个不同申请，其中 18398 案的索引图片列仍显示“无”，确认此问题并非仅存在于样本。

### P1：只读取 workflow_requestLog，却标记“完整历史”

位置：旧 OA 加载段约第 571 行仅查询 `workflow_requestLog`；第 1337 行将这一单表结果标为“完整历史”。旧导出 `scripts/e9_opinion_export.py:170` 还读取 `workflow_approvelog`。

当前不能证明本次三件套已覆盖旧导出可取得的全部意见。建议按旧脚本策略合并两个来源，保留来源表及原始记录 ID，核验重复记录后再统计；完成前应明确标为“workflow_requestLog 日志”。

### P2：加载阶段案件计数为 0/0，容易被理解为页面没有数据

位置：第 1434 行才在逐案渲染前赋值 `prog.cases["total"]`。实际案件早在 MySQL 加载阶段就已取得，但随后十多分钟的旧 OA 加载期间，页面仍显示案件 0/0、速度 0、暂无覆盖统计。

本次直接请求 8771 页面和 API 都返回 200，阶段详情持续更新；该情况不是进度文件丢失。建议在 MySQL 索引完成时写入案件总数，明确提示“正在准备，尚未生成 MD”；旧 OA 阶段提供已加载请求数/总数，不对准备阶段估算 MD 剩余时间。

### P2：迁移附件命名空间靠数值阈值判断，仍需证据核验

位置：第 634 行附近，迁移案件中小于 `10**12` 的文件 ID 会优先按旧 `imagefileid` 解析，同号新文件直接不采信。这是启发式规则，不是逐条来源证明。

真实存在“迁移案件后续追加了新附件”时，该规则可能错判。建议将阈值仅作为候选，补充旧表单文件字段、同号元数据及内容核验；冲突记录标来源待确认。此次未证明已有样本出现错绑，不把此项计为已发生的全量错误数。

### P2：流程按“实例ID＋来源”去重，未来可能重复渲染同一流程

位置：第 440–442 行用 `(pid, src)` 去重；`sec_flow()` 则逐条关联重新渲染并累计意见。申请和档案若指向同一真实新库流程，会产生两次相同审批内容和重复计数。

样本已存在同一旧 requestid 从申请/档案两条来源进入关系表的情况；本次数据库抽查未找到申请与档案同时指向同一 HCCX 流程的记录，因此此项是明确的代码边界风险，不宣称当前原生样本已经重复。建议按流程 ID 去重，来源保留为数组。
