# 合同审查三栏滚动协调调研与修复（2026-11-10）

## 原实现的问题

- claimDriver 仅在没有驱动栏时接管，以 140ms 定时器释放；快速换栏的真实手势被旧栏锁阻挡。滚动条拖动、键盘也没有接管入口。
- 正文滚动按像素复制；批注反向联动按最近卡片跳到条款顶部，两个方向不连续。
- offsetTop 属于 offsetParent 坐标，不能直接当成滚动容器内坐标；点击定位也有同一问题。
- 滚动过程中反复 scrollIntoView(smooth) 会启动新的异步滚动，且可能影响外层滚动容器。
- 每次滚动遍历批注和条款并交错读写布局，增加长合同的主线程负担。

## 采用方案

保留浏览器原生滚轮/触控板滚动，不 preventDefault，不添加模拟惯性。手势发生在哪一栏，该栏立即成为唯一驱动源；程序写入的从栏位置不会反向驱动。点击定位有单独状态，可被真实输入打断，并遵循减少动态效果的系统偏好。

左右正文以对应条款建立锚点；正文与右栏以实际可见卡片和所属条款建立锚点。锚点之间做分段线性插值；加入首尾边界，处理短内容、空筛选、重复/乱序锚点。筛选或异步展开后重建测量缓存。一个条款有多条批注时，重复正文锚点保留首个可用点，保证映射单调。

滚动帧内只查缓存并二分定位，合并从栏写入。ResizeObserver、MutationObserver、窗口尺寸和字体加载用于使缓存失效。MutationObserver 不监听高亮 class，避免把高亮变更当作布局变更。重新渲染后解除旧卡片监听。

## 官方资料及对本项目的意义

- [MDN：scroll event](https://developer.mozilla.org/en-US/docs/Web/API/Document/scroll_event)：高频事件中应减少昂贵工作；rAF 与滚动事件频率相近，不能把 rAF 本身当作降频。本次主要收益来自缓存几何和去除逐帧全量遍历。
- [Chrome：默认快速滚轮](https://developer.chrome.com/blog/scrolling-intervention-2/)：不必要的可取消滚轮监听会阻塞浏览器滚动；本次保持 passive 监听。
- [MDN：scrollTop](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollTop)：滚动值可能为小数，部分环境有越界值；本次使用容差并夹取边界。
- [MDN：scrollIntoView](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollIntoView)：该 API 可能影响多个祖先滚动容器；本次点击仅对目标栏调用 scrollTo，普通联动不用 smooth。
- [MDN：ResizeObserver](https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver)：用于响应元素尺寸变化，覆盖卡片展开和容器尺寸变化。
- [W3C：CSS Overscroll Behavior](https://www.w3.org/TR/css-overscroll-1/)：用 CSS 控制滚动链；本次三栏设置 contain，防止边界处把滚动传到外层页面。

上述协调算法是结合本项目结构得出的工程方案，并非浏览器规范规定的唯一算法。

## 验证及边界

- Node 执行页面实际内联控制器，覆盖插值、边界、从栏防回灌、立即接管、右栏小步连续性、导航隔离、空筛选、零滚动范围、尺寸变化。
- 页面/API 与控制器回归测试共 12 项通过；Python 编译与改动空白检查通过。
- Edge headless 真实 DOM 布局测试（24 条不等高条款、24 张卡片）通过：联动、防回灌、接管、连续性、首尾对齐。通过 CDP 等待真实帧；dump-dom 的虚拟时间模式会跳过部分动画帧，不能用于此项判断。
- 浏览器测试使用合成手势与程序滚动，不代表物理鼠标/触控板手感验收。未测量真实业务大合同的 FPS、输入延迟和不同刷新率；不声称达到特定帧率。

## 补充排查与专项优化：右侧批注栏驱动左中两栏失效问题（2026-11-10 深度优化）

### 1. 现象与根因定位
用户反馈“左边能带动中间和右边，中间能带动左边和右边，右边带不动左边和中间”。经真实 Edge Headless CDP 录屏与运行时几何数据倾倒，定位到以下两个关键缺陷：
1. **贪心单调筛选导致锚点退化断崖**：
   原算法在建立 `detail -> std/rev` 候选锚点时，使用 `point[0] > previous[0] && point[1] > previous[1]` 的贪心过滤。但在实际合同中，同一个条款可能关联多张批注卡片（甚至存在局部倒序或短距离重叠），贪心算法在遇到首个非递增卡片后，直接丢弃了其后**所有的后续锚点**！
   实测中 48 张批注卡片的映射表直接退化为只有 3 个孤立点：`[0, 0]`, `[101, 4096]`, `[12504, 4189]`。右栏滚动至 101px 后，中间直接跳变至 4096px（底端截断），导致用户拖拽右栏滚动条或在右栏滚轮时，正文几乎“卡死”或“带不动”。
2. **两两独立映射缺乏传递一致性（缺少统一基准坐标）**：
   原实现分别为 `std->rev`, `std->detail`, `detail->std`, `detail->rev` 独立贪心构建锚点，导致 A->B 与 B->A 不对称，手势在右栏释放时与从属栏计算值失配。

### 2. 业界调研方案参考
- **GNOME Meld (`meld/filediff.py`, `misc.py`)**：
  三栏协同滚动（Three-pane diff）中，Meld 采用**以中间栏为中心枢纽（Hub-based mapping）**的拓扑：所有栏位均建立与中间栏的双向单射。无论左栏、中栏还是右栏触发滚动，映射均以中间栏的逻辑行/内容坐标作为媒介，实现闭环一致性（A->B->A 恒等）。
  同时引入 **`calc_syncpoint` 动态视准线**：首屏由 0 线性过渡到 0.5（视口中间），尾屏由 0.5 线性过渡到 1.0（视口底部），彻底解决了“首尾屏条款因视口高度差被裁切不可见”的问题。
- **VS Code Markdown Preview (`scroll-sync.ts`)**：
  采用代码行号/标记块的二分查找与分段线性插值，利用严格保序算法映射内容位置，并根据容器尺寸与卡片展开状态动态更新几何模型。

### 3. 重构优化方案与落地
1. **LIS 最长公共递增单调链 (`monotoneAnchors`)**：
   将原贪心过滤替换为 $O(n \log n)$ 的 Patience 排序 LIS 算法。遇到乱序或重叠锚点时，仅剔除局部逆序点，保留全局最长递增链。实测 48 张批注卡片与 37 个条款块恢复出 38+ 个高质量连续锚点。
2. **中心枢纽双向映射体系（Hub Topology）**：
   以送审稿正文（`rev` 栏）为全局 Hub。左栏与右栏分别维护与 Hub 的可逆双向折线映射表（`toHub` / `toPane`）。任何一栏滚动均可精准推导出其余两栏的目标 `scrollTop`，且换栏时位置无跳动。
3. **Meld 动态视准线（Reading Line Interpolation）**：
   各栏加入 `readingLineAnchors`，统一视准线几何变换，确保首屏第 1 条款与末屏条款都能精准对齐居中。
4. **滚动条拖拽与异步刷新支持**：
   针对右侧滚动条拖拽事件，`followerPositions` 记录预期位置，避免从栏产生回灌锁死；在卡片展开、AI 流式研判更新、窗口 Resize 时通过 `scheduleResync` 重新测量几何并对齐，同时在重绘列表时保持用户当前的 `scrollTop`。

### 4. 验证结果
- **CDP 真实浏览器联动验证**：
  - 右栏滚轮步进 120px：左中两栏自适应步进（如 `[1440, 1444, 5796]` $\rightarrow$ `[1718, 1722, 6516]` $\rightarrow$ `[1947, 1951, 7236]`），左中右三栏顺滑同步。
  - 右栏滚动条鼠标按住拖拽：从栏平滑跟随（达到 `[2786, 2790, 10192]`），完全解决“右边带不动左边和中间”的问题。
- **自动化测试**：
  - Node 控制器回归测试 `test_three_way_scroll.py` 100% 通过（涵盖右栏驱动、防回灌、首尾对齐、单调性）。
  - 全套单元测试（88 项通过，14 项受控跳过）回归全绿。
